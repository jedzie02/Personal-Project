# Open Play Sessions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the venue run scheduled open play sessions that logged-in players join and pay for per head by card, with the paid join reserving the spot.

**Architecture:** Two new tables (`open_play_sessions`, `open_play_entries`) plus an atomic Postgres function that claims a spot. A session creates one hold booking so the existing grid and overlap check block that court time. A join starts a Stripe checkout (30-minute hold, matching Stripe's minimum expiry). The existing Stripe webhook and the redirect-time sync both call one idempotent `markEntryPaid`, which decides the outcome with a pure function and sends the receipt only on the first `paid` transition. Existing `bookings` and `payments` columns are untouched.

**Tech Stack:** Next.js (App Router, server actions, Route Handler), Supabase (Postgres, service-role admin client), Stripe Checkout, Gmail SMTP sender in `email.service.ts`, Tailwind, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-03-open-play-design.md`

## Global Constraints

- Do not alter columns or constraints of `bookings` or `payments`. The only write to `bookings` is one hold row per session; stop and ask the owner if the live table rejects it.
- Schema changes ship as `supabase/migrations/20261103_open_play.sql`, which the owner runs manually in Supabase. Writes use `createAdminClient()` (needs `SUPABASE_SERVICE_ROLE_KEY`), like `markPaymentFailed`.
- Stripe: currency `"php"`, amounts in centavos (`Math.round(amount * 100)`), card only, checkout `expires_at` = 30 minutes from creation, metadata key `openPlayEntryId`.
- Hold booking: status `confirmed`, payment method exactly `"Open Play hold"`, price 0, owned by the creating admin's profile id.
- Hold length: 30 minutes. Entry statuses exactly: `pending`, `paid`, `cancelled`, `needs_refund`. Session statuses: `scheduled`, `cancelled`.
- Sessions use whole hours inside 09:00–23:00 and cannot start in the past (Philippine time via `getManilaNow`). Players: one entry per (session, customer). Currency symbol `₱`, 12-hour AM/PM times, `text-xs` minimum, light and dark mode per `DESIGN.md`.
- Files tested by Vitest use relative imports (no `@/` alias).
- No git commits or pushes until the user asks.

## Review Focus

1. **Last-spot race:** two players joining the last spot at once must not both succeed. The `claim_open_play_spot` SQL function does the count-and-insert in one transaction under a session row lock; verify by reading the SQL, and pin the capacity math with `computeSpotsLeft` tests.
2. **Duplicate payment signals:** the webhook and the confirmation-page sync can both report the same payment, and Stripe can redeliver. `decideEntryOutcome` must return `"noop"` for an already `paid` entry so no second receipt is sent.
3. **Payment after cancel or expiry:** a payment for a cancelled session becomes `needs_refund`; a payment after the hold expired becomes `needs_refund` only if the session is full, otherwise `paid`.
4. **Bad session input:** end not after start, non-whole hours, outside 09:00–23:00, past start, cap < 1 or non-integer, negative or non-numeric price must all be rejected with a message, never inserted.
5. **Session creation atomicity:** if the court time is already booked, or the session insert fails after the hold was created, no orphan hold booking or session may remain.
